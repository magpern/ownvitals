# Languages: response codes and health wording

Written by #250 (G4, ADR 0015 sections 5 and 6). The runtime and the catalogue rules are in
[frontend.md](frontend.md) ("Languages"); this file is the code list and the owner's review list.

## Response codes (section 6)

A user-facing response carries a stable code, never an English sentence. Parameters are numbers,
ISO dates or allowlisted enums, never free text or another user's values. Log lines, admin-only
output and the CLI stay English.

- The list is `backend/src/ownvitals/response_codes.py`, one set per route family (`auth`, `jobs`,
  `job_failures`, `connections`, `views`).
- `backend/tests/test_response_codes.py` checks that the jobs and connections routes emit only
  listed codes, that `assert_response_code(family, body)` fails on an unknown one, and that
  `frontend/src/api/codes.json` equals the list.
- The frontend words a code with `codeMessage` (`src/api/codes.ts`): `errors.reason.<code>` first,
  then `codes.code.<code>`; an unknown code shows `errors.generic`. `src/api/codes.test.ts` fails
  when a listed code has no English entry.

Adding a code: add it to its family, regenerate the list, add the English text to
`src/i18n/en/codes.ts` (and the English copy to `sv/codes.ts`, listed in `untranslated.ts`):

```bash
cd backend && uv run python -c "import json; from ownvitals.response_codes import all_codes; \
print(json.dumps(all_codes(), indent=2))" > ../frontend/src/api/codes.json
```

Replaced sentences: `error_message` of a job (now `error_category` alone), `removal` of a
disconnect and an account deletion (now `revoke_incomplete`), `method.text` of a metric detail (now
`method.code` `daily_summary`, worded from `method.parameters`).

## Health wording (section 5)

**Health wording** is the owner's medical-claims review at M8 (PLAN-operations section 9.3), in
both languages. Every key of `src/i18n/*/health.ts` is health wording; a translation may not
change a tier, a threshold or a confidence, or add advice the English text does not give. Nothing
translated is stored: findings hold `rule_id`, `tier` and `evidence`, and the page words them
(ADR 0010 section 8). `frontend/src/api/rules.json` lists every rule id of the specs and
`codes.test.ts` fails when one has no name and text.

Tiers and severities:

- `health.tier.device`, `health.tier.trend`, `health.tier.experimental`, `health.tier.system`,
  `health.tier.experimental.note`
- `findings.isnt.device`, `findings.isnt.trend`, `findings.isnt.experimental`,
  `findings.isnt.system` ("What it isn't" on the findings screen) are health wording too
- `health.severity.urgent`, `health.severity.attention`, `health.severity.info`

Rules (key prefix `health.rule.<rule_id>`), one name and one text each:

- `health.rule.B2.name`, `health.rule.B2.text`
- `health.rule.B3.name`, `health.rule.B3.text`
- `health.rule.B4.name`, `health.rule.B4.text`
- `health.rule.B5.name`, `health.rule.B5.text`
- `health.rule.B6.name`, `health.rule.B6.text`
- `health.rule.C1.name`, `health.rule.C1.text`
- `health.rule.C1x.name`, `health.rule.C1x.text`
- `health.rule.C2.name`, `health.rule.C2.text`
- `health.rule.E1.name`, `health.rule.E1.text`
- `health.rule.E2.name`, `health.rule.E2.text`
- `health.rule.E3.name`, `health.rule.E3.text`
- `health.rule.E4.name`, `health.rule.E4.text`
- `health.rule.E6.name`, `health.rule.E6.text`
- `health.rule.N2:guided.name`, `health.rule.N2:guided.text`

- `health.rule.N3.name`, `health.rule.N3.text`

- `health.rule.Q1:import_incomplete.name`, `health.rule.Q1:import_incomplete.text`

- `health.rule.Q1:reconnect.name`, `health.rule.Q1:reconnect.text`

E5 is deferred (ADR 0010) and has no entry; N1 is a gate, not a rule. Placeholders in the texts
are filled from the finding's `evidence` by the screens that show findings (M6). `interpolate`
accepts no `_`, so the names are camelCase; the mapping is:

| Rule | Placeholder | Evidence key |
|---|---|---|
| E2 | `count`, `total` | not written yet (no E2 producer exists): the issue that writes E2 names the evidence keys and updates this row |
| B1 | `gainKg` | `gain_kg` |
| B2, B4, B5, C2, N3 | `windowDays` | `window_days` |
| B3 | `ratio`, `threshold` | `ratio`, `threshold` |
| B6, N5 | `ratio`, `threshold` | `median_symmetry_index`, `threshold` |
| C1 | `bpm`, `runDays` | `margin_bpm`, `run_days` |
| C1x | `runDays` | `run_days` |
| N2:routine | `runDays` | `run_measure_days` |
| Q1:no_weigh_in | `days` | `days_since` |

E2 and E3 are device flags, not atrial fibrillation: E1 is `afib` = 1 or `afib_details` 1, 11, 12;
E2 is at least 3 of the last 10 ECGs with `afib_details` 2 or 5 (inconclusive or noisy); E3 is
`afib_details` 6 or 7 (low or high heart rate); E4 uses fixed clinical limits (QTc, PR, QRS),
E6 the personal 90-day range (ADR 0006 section 11). A test keeps E2 and E3 free of "atrial
fibrillation".

## Swedish glossary (G6)

Tone: plain, calm Swedish; "du" form; no exclamation marks. A term has one translation everywhere
(app, mail, health wording). Brand and product names (ownvitals, Withings, Google) and units
(kg, bpm) stay. Plurals use `one` and `other`.

| English | Swedish | English | Swedish |
|---|---|---|---|
| finding | fynd | measurement, metric | mätvärde |
| reading | avläsning | trend | trend |
| experimental | experimentell | typical / usual range | vanligt intervall |
| device | enhet | connection | anslutning |
| sign in / out | logga in / ut | sign up, create account | skapa konto |
| authenticator app | autentiseringsapp | recovery code | återställningskod |
| two-factor authentication | tvåfaktorsautentisering | passkey | passkey |
| invite code | inbjudningskod | reconnect | anslut igen |
| session | session | step up ("Confirm it's you") | bekräfta att det är du |
| weigh-in | vägning | admin | administration |

Words that read the same in both languages stay, and the key is listed (with a reason) in
`SAME_IN_SV` of `src/i18n/untranslated.ts` because the guard compares text: `health.tier.trend`, `ui.tier.trend`,
`ui.tier.system`, `shell.nav.data`. The Swedish health wording (`sv/health.ts`) keeps the meaning
of the English text exactly and stays on the M8 medical-claims review list above.

## Mail (section 7)

Written by #253 (G5). The outbox row is unchanged (kind, recipient, link); the language is looked
up when web sends, like the address.

- Outbox templates: `backend/src/ownvitals/notify/templates/{en,sv}.py`, one table per manifest
  code, the same kinds, `{link}` exactly once and no other placeholder. Account mails:
  `backend/src/ownvitals/auth/mail_texts/{en,sv}.py`, the same keys and placeholders in each.
- Which language: `notify/locale_policy.py` (pure). Outbox mail to a user uses the stored
  `users.locale` (`NULL` or a code switched off is `en`); owner notices are `en`; sign-up
  confirmation, "account exists" and the reset link use the account's stored language, else the
  request's; everything else is `en`. The lookups are `auth/recipients.py` (guard 8) and return
  only a manifest code that is also offered.
- The code is the mail's `Content-Language` (`MailMessage.locale`, which refuses any other value).
  Dates are ISO; no `strftime` month or day names and no `setlocale`.
- Untranslated lists: `notify/templates/untranslated.py` and `auth/mail_texts/untranslated.py`.
  Both are empty since G6 (#254): every Swedish mail text is translated. A new English text is
  copied to `sv`, listed, and translated by the next translation PR.
- Golden files: `backend/tests/mail_golden/{outbox,auth}/<locale>/`. After an intended text
  change: `WRITE_MAIL_GOLDEN=1 uv run pytest tests/test_notify_templates_locales.py
  tests/test_auth_mail_locales.py`, then review the diff.

## Add a language (G7)

Written by #255. A code in `frontend/src/i18n/locales.json` is refused by CI until every piece
below exists: `backend/tests/test_locale_guard.py` (checker `backend/tests/localeguard.py`) names
each missing piece, and the frontend guards (`catalogue.test.ts`, `hardcoded.test.ts`) check the
catalogue. The guard is proved on a temporary copy with a fake code, one test per piece.

1. **Catalogue.** `frontend/src/i18n/<code>/` with the same areas and keys as `en` (copy `sv`),
   its entry in `LOADERS` (`store.ts`) and the `Locale` type (`locale.ts`). English copies are
   listed in `untranslated.ts` until translated.
2. **Mail.** `notify/templates/<code>.py` and `auth/mail_texts/<code>.py`, registered in their
   `TABLES`, with the same kinds and placeholders; untranslated copies go in the `untranslated.py`
   lists.
3. **Migration.** A new Alembic migration drops and re-adds the `CHECK` of `users.locale`,
   `pending_signups.locale` and `oauth_flows.locale` with the new code, and `LOCALE_CHECK` in
   `auth/tables.py` changes with it (the outbox row has no language column). Never edit 0017.
4. **Picker.** The language's own name in `LOCALE_NAMES` and its `Intl` tag in `INTL_TAG`
   (`locale.ts`); the picker and Settings read both.
5. **Golden files.** `WRITE_MAIL_GOLDEN=1 uv run pytest tests/test_notify_templates_locales.py
   tests/test_auth_mail_locales.py`, then review `backend/tests/mail_golden/{outbox,auth}/<code>/`.
6. **Health wording.** `<code>/health.ts` keeps the English meaning, tiers, thresholds and
   confidences exactly and joins the owner's M8 medical-claims review list (above).
7. **Translation PR rule.** A translation PR changes only that language's files, the untranslated
   lists and the golden files; it never changes English text, keys, a tier or a threshold. A glossary
   section for the language goes in this file first.
8. **Switch.** `OWNVITALS_LOCALES` offers it; `en` is always on. Run `e2e/specs/i18n.spec.ts`.
